# MASTER DEVELOPMENT PROMPT — PS6: PLACEMENT HUB
## Build a Complete, Production-Structured, Full-Stack Evidence-Based Campus Placement Platform

### 1. ROLE AND MISSION

Act as a senior full-stack software engineer, solution architect, UI/UX designer, database engineer, AI engineer and application security specialist.

Build a complete, functional, responsive web application called **Placement Hub**.

This application addresses the following problem:

College students often apply to many jobs using generic resumes and unverified skill claims. Placement officers receive openings through multiple sources, struggle to track candidates and duplicate postings, and lack a reliable way to rank students. Employers need shortlists based on demonstrable skills rather than unsupported resume statements.

Your mission is to implement a unified evidence-based placement management platform that connects:

1. Employer job requirements.
2. Students' actual skills and supporting evidence.
3. Explainable job-fit scoring and skill-gap analysis.
4. Truthful, job-specific resume generation.
5. Centralized application tracking.
6. Batch-wide student ranking.
7. Recruiter shortlisting and optional alumni and interview-question features.

**Core product principle: Every skill claim, match recommendation and generated resume bullet must be traceable to supporting evidence or explicitly identified as unverified.**

Do not build a generic job board with decorative AI features. Implement the actual business logic behind the product.

# 4. USER ROLES AND ACCESS CONTROL

Implement three principal roles, with optional administrator support.

## A. Student

Students can:

- Register and sign in.
- Complete their profile.
- Add skills and link supporting evidence.
- Upload project documents and permitted evidence files.
- Connect a GitHub account or provide repository URLs.
- View evidence-verification status.
- Browse and filter suitable jobs.
- View their job-fit score and matching explanations.
- Review missing skills and recommended next steps.
- Generate and download tailored resumes.
- Manage their job applications.
- Track interviews, results and offers.
- View their own activity and application history.

Students must not be able to verify their own evidence by changing a status field or sending an unauthorized API request.

## B. Placement Officer

Placement officers can:

- View and manage authorized students.
- Create, import and edit job openings.
- Manage job sources and duplicate postings.
- Review submitted skill evidence.
- Approve, reject or request additional evidence with a reason.
- Create or review assessments and assessment results.
- Run matching against an entire eligible student batch.
- View ranked candidate lists.
- Understand why candidates received particular scores.
- View unsupported claims and incomplete evidence.
- Track applications from submission to final outcome.
- Update application stages according to permissions.
- View placement analytics.
- Export authorized reports to CSV.

A placement officer should not be able to silently alter evidence, assessments or historical application outcomes. Record important changes in an audit log.

## C. Recruiter

Recruiters can:

- View jobs associated with their company.
- Create or manage authorized job openings.
- Specify required and preferred skills.
- View candidates authorized for their openings.
- See ranked shortlists and evidence summaries.
- View resume versions shared with them.
- Update authorized recruitment-stage information.
- Record interview outcomes where permitted.

Recruiters must not automatically gain access to every student's personal information, private evidence or unrelated job applications.

## D. Administrator

Provide an optional administrative role for managing users, roles, global configuration and integrations.

Implement backend role checks on every protected endpoint. Frontend route guards alone are insufficient.

# 7. STUDENT PROFILE AND EVIDENCE VERIFICATION

This is one of the core differentiators of Placement Hub.

Do not treat a manually entered skill as verified simply because it appears on a student's profile.

## Supported evidence types

Implement a flexible evidence system that supports:

- Assessment results.
- Evaluated academic projects.
- Personal and team projects.
- GitHub repositories.
- Certifications.
- Demonstration URLs.
- Uploaded reports and project documents.
- Instructor or reviewer feedback.

## Evidence data model

Each evidence record should include, as applicable:

- Evidence ID.
- Student ID.
- Evidence type.
- Relevant skill IDs.
- Title and description.
- Source URL or secure file reference.
- Date submitted.
- Issuing organization or assessor when relevant.
- Assessment score and maximum score when applicable.
- Reviewer ID.
- Verification status.
- Reviewer notes.
- Created and updated timestamps.
- Provenance information.

## Evidence statuses

Use explicit states:

- `unverified`
- `pending_review`
- `verified`
- `rejected`
- `needs_more_evidence`

Only an authorized reviewer or a documented automated verification rule may transition evidence to a verified state.

Every reviewer decision should record the actor, time and reason.

## Skill verification rules

Examples:

- An assessment score can support a skill when the assessment identity, score and scoring rules are recorded.
- A project can support a skill only after an appropriate review or evaluation rule.
- A GitHub repository can provide metadata and code evidence but must not automatically establish professional-level mastery.
- A certification can establish that a certificate was submitted; stronger verification may require issuer or credential checks.
- Student self-reported skills must remain distinguishable from independently supported skills.

Do not invent verification results.

For a hackathon demonstration, use seed records explicitly marked as sample verified, sample pending or sample unverified.

## Evidence viewer

Build a usable evidence-review interface showing:

- Skill supported.
- Evidence source.
- Verification history.
- Review status.
- Reviewer notes.
- Relevant repository, assessment or project information.

Provide approve, reject and request-more-evidence controls for authorized users.

Each operation must call the backend and update the interface using the returned result.

# 8. SKILL NORMALIZATION ENGINE

Different job sources use different names for the same skill.

Implement a canonical skill catalog with aliases.

Examples:

- `ReactJS` → `React`
- `React.js` → `React`
- `React JS` → `React`
- `Postgres` → `PostgreSQL`
- `JS` → `JavaScript` only when context establishes that meaning.

Store:

- Canonical skill ID.
- Canonical display name.
- Aliases.
- Optional category.
- Version or variant where relevant.

Normalization must be case-insensitive and whitespace-insensitive where appropriate.

Do not collapse distinct technologies into the same skill. For example, Java and JavaScript are different skills. React and React Native are related but must not automatically become identical.

Use a deterministic alias dictionary first. Add context-aware or semantic matching only when needed.

Allow placement officers to review uncertain mappings and improve the canonical catalog.

# 10. JOB-FIT SCORING ENGINE

Implement an explainable and independently testable matching service.

The system should compare job requirements with the student's evidence-backed profile.

## Initial scoring formula

For a given job and student, calculate:

Fit score = 100 × (sum of requirement weight × evidence match value) / (sum of requirement weights)

Use the following initial configurable weights:

- Required skill: weight 4.
- Preferred skill: weight 1.

Each requirement has an evidence match value between 0 and 1.

An example policy:

- No submitted supporting evidence: 0.
- Relevant evidence submitted but not yet reviewed: partial provisional credit.
- Relevant evidence verified: credit according to the configured verification and relevance rules.
- Rejected or irrelevant evidence: no positive credit from that evidence.

These values are configurable policy examples, not universal measures of ability.

When multiple evidence items support a skill, deduplicate the underlying skill contribution so one student cannot inflate their score merely by attaching numerous similar links.

Keep the following concepts separate:

- Skill claimed.
- Evidence submitted.
- Evidence verification status.
- Evidence relevance.
- Assessment result.
- Match score for a job.

## Required skill handling

Show required-skill coverage separately from the overall fit score.

If a student lacks evidence for a critical required skill, explicitly flag the gap.

Do not automatically describe a missing skill as a confirmed inability to perform the work.

Allow the placement officer to configure whether certain eligibility requirements are hard filters or review flags. Do not silently apply academic, demographic or other discriminatory rules.

## Explainability

For every student-job pair, return:

- Overall fit score.
- Required-skill coverage.
- Preferred-skill coverage.
- Matching skills.
- Missing or insufficiently supported skills.
- Supporting evidence references.
- Evidence verification states.
- Explanation of the main factors affecting the score.
- Recommendation for closing relevant skill gaps.

Store the scoring algorithm version and the relevant inputs so results can be reproduced or audited.

Build unit tests for correct scoring, missing evidence, rejected evidence, duplicate evidence and edge cases.

# 12. TRUTHFUL, ATS-FRIENDLY RESUME GENERATOR

Build a working resume-generation workflow.

## Inputs

- Student's profile.
- Selected job opening.
- Supporting evidence.
- Approved or suitably supported project details.
- Student-approved personal and education information.

## Resume sections

Include:

- Name and contact information.
- Professional summary.
- Education.
- Relevant technical skills.
- Relevant projects.
- Verified or appropriately supported experience.
- Certifications and achievements with supporting details where available.

Adapt section ordering and bullet selection to the selected job.

## Evidence traceability

Every generated factual achievement or project bullet must link internally to one or more evidence records.

For every bullet, store:

- Resume ID.
- Bullet text.
- Supporting evidence IDs.
- Related skills.
- Claim-review status.

The resume interface should let students view the evidence behind each bullet.

When no supporting evidence exists:

- Do not invent a replacement fact.
- Do not add fake proficiency, work experience or achievements.
- Mark the unsupported claim for review or exclude it from the generated resume.
- Explain what information or evidence the student could provide.

If an uploaded resume contains unverified claims, flag those claims for review. Do not silently treat them as false, and do not silently accept them as verified.

## AI use

An optional LLM can help rewrite verified project descriptions and select relevant content for a job.

The LLM must not invent metrics, business impact, tools used, employment history or project achievements.

Use a factual-claim validation layer and retain evidence references outside the language model's free-form output.

If no AI API key is available, provide a deterministic template-based resume generator. The platform must remain functional without a paid AI service.

## Output formats

Generate:

- A one-page, ATS-friendly PDF.
- Optional DOCX.
- Editable resume preview.
- Resume version history.
- Download and regeneration controls.

Avoid complex tables, graphics and multi-column layouts in the exported resume unless explicitly requested. Use clear headings, selectable text and standard formatting.

Before export, display validation results for unsupported claims and missing required fields.
